# DSH plugins in the iOS app

The app has two interfaces onto the same engine and profile. The user normally works in the **native interface**, built in SwiftUI. The **web interface** is the official DSH Web UI, opened from 网页版 (Web version) on the app's 探索 (Explore) tab (in the sidebar on an iPad before iOS 18). A plugin does not reach both in the same way:

| Part of a plugin | Native interface | Web interface |
|---|---|---|
| Host half: what runs in the engine, such as tools and settings | Works | Works |
| Browser half: `dsh.client` in `package.json`, the `./client` export, slots such as `sidebar.panellist` and `main`, React pages and panels | **Never runs** | Works |

- **A plugin that only adds interface is invisible in the native interface.** No sidebar entry, panel, or custom page appears there. Its card still shows under 插件 as installed and running, because the engine did load it.
- **The built-in DS Bot plugin (`ds-bot`) is the exception.** The app ships it pinned to one version and draws its Bots, group chats, schedules and forms in native pages (the app's Bot tab; on an iPad before iOS 18 the Bot card in the sidebar). Its own web page is not needed there, and it cannot be updated or replaced from the app.
- **The built-in image generation plugin (`dsh-image-gen`) is the other exception.** The app ships it pinned to one version and draws its settings (Settings → 生图 (Image Generation), the top row of the 探索 (Explore) tab), the pictures its tools make in the conversation, and a markup that sends a marked copy of a conversation picture with a message. Its infinite canvas, gallery, Studio and multi-model comparison are its own pages in the web version. It cannot be updated or replaced from the app.
- **A few official plugins are also drawn natively.** The app draws them itself rather than running their browser half. 思考过程翻译 (`@deepseek-ai/dsh-experimental-cot-translation-bundle`, reasoning translation): while it is enabled, the full reasoning sheet (tap a reasoning row) shows the translation with a switch back to the original. The collapsed row stays in the original language. This does not extend to other plugins, official or not.
- **Connectors are services the user signs in to once** (GitHub, Notion, Linear and the like), under 连接器 (Connectors) on the app's 探索 (Explore) tab (in the sidebar on an iPad before iOS 18). A connected service is listed there once the DS Bot plugin is running. A connected service is an MCP server mounted for the whole engine, so its tools are there in every session as `mcp__<id>__*`, this one included, not only for Bots. If a task needs a service whose tools you do not have, ask the user to connect it there; you cannot connect one yourself. Only connectors at a web address work: one that starts a local command cannot run here.
- **Build Host-only plugins.** Do not write a browser half unless the user asks by name for something in the web interface. The plugin guide in the `dsh-doc` skill is written for the Web UI: its UI plugin template, slots, pages and panels all land under 网页版, and the user, who works in the native interface, would see nothing.
- **Turn visual requests into something that shows.** If the user wants to see or tap something (a page, chart, widget, a tool with buttons), say before building that a plugin cannot show it in this app, and offer a mini app instead: read the `mini-apps` skill. If what they want is a capability, put it in the Host half as a tool you can call. If they still want the plugin's interface, build it and say it appears only under 网页版.
- **Report where it appears.** Being in the profile, loading in the engine, or working in a web page does not show that it appears in the native interface. Name the interface you checked, and do not say a plugin's interface is in the app without saying it is the web interface.
- **`localStorage` belongs to the web interface.** Data a browser half keeps there never reaches the engine or the native interface.
- **A plugin that never finishes loading keeps the whole app out.** The interface opens only once every plugin has loaded, so do not make a plugin's startup wait on anything that can hang, such as a network request. If one does, the launch screen offers 停用第三方插件并重启: it switches off every plugin that is neither DSH's own (`@deepseek-ai/…`) nor built into the app, leaves them installed, and lists them once the app is in. The user then switches them back on one at a time under 插件 to find the one that hangs.
- **Dynamic Cordis plugins** with Client code cannot be activated from the native interface. Define a Host-only version, or run it from the web interface.
- **Device capabilities are for you, not for plugins.** Building a plugin on them is out of scope — do not do it and do not offer to, even if the user's idea would work. Say why if they ask: nothing is promised here, the names and arguments change between versions, and a plugin that wrote them down breaks silently on an update. You are fine because you re-read the skill every session.
- **A plugin they install can still reach them**, and nothing stops that: whatever the app is allowed to do, a plugin they install is allowed to do. That is a fact about installing plugins, so say it plainly when you build one for them — it is the reason the install warning reads the way it does.
